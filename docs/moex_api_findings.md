# trades.json — критическое ограничение

- **Пагинация через `start` НЕ РАБОТАЕТ.** Сервер всегда возвращает один и тот же блок из 5000 записей, независимо от значения `start`.
- **Максимум 5000 строк за один запрос.** Это окно соответствует ~1–3 минутам торгов по SBER в основную сессию.
- **Следствие:** live_producer должен опрашивать эндпоинт каждые 5–10 секунд, чтобы не терять сделки. Догоняющая пагинация невозможна.
- **Следствие:** replay_producer НЕ использует trades.json. Только candles.json?interval=1.
- **Следствие:** trade_id (TRADENO) + ON CONFLICT DO NOTHING — обязательны для защиты от дублей при перезапуске.

# Уточнения

## Пагинация: подтверждено community (Smart-Lab, 2023)

Известное ограничение ISS для endpoint'ов типа `trades`, не связано с нашим кодом. `start` работает для других типов ISS-эндпоинтов (`history`, `securities`), но не для потока сделок.

## Открытый вопрос (эксперимент запущен): скользящее окно или статичное?

Результат теста с разницей в 10 минут: Статичное, если смотреть сначала. Можно получить скользящее, используя `?reversed=1`.

## Лимиты (неофициальные, по данным сообщества)

- ~100 000 запросов/сутки
- ~20 запросов/сек.

Наш план: (3 тикера \* interval=5s, 24/7) = ~51 840 запросов/сутки ≈ 52% от лимита — запас достаточный.

## Решение по времени сделки

Канонический `trade_time` = `TRADEDATE` + `TRADETIME` (время исполнения). Не `SYSTIME` (время попадания в ISS, есть небольшой лаг обработки).

## Неразобранные поля (не блокируют MVP)

`PERIOD` — вероятно код торгового периода/аукциона, точный смысл не подтверждён документацией. Сохраняем как есть, логику на нём не строим.

# Решение по live-эндпоинту

## Базовый `trades.json` — статичное окно (подтверждено экспериментом)

Диапазон `TRADENO` и времени не меняется при повторных запросах с разницей
10-20 минут. **Не использовать для живого потока.**

## `trades.json?reversed=1` — рабочее решение

Три последовательных запроса (интервалы 10с, 5с) показали растущий диапазон
`TRADENO` — окно реально скользит. **ИСПОЛЬЗУЕМ ЭТОТ ВАРИАНТ в `live_producer`.**

## `candles.json` без `from`/`till` — отдаёт данные с начала истории (2011), не последние

Важно для `replay`: всегда передавать явный диапазон дат.

# Уточнение по планированию live_producer

Текущая схема "работа -> sleep(interval)" даёт реальный период = время_работы +
interval, а не строго interval (дрейф). Осознанно не исправляется: запас по
объёму окна (5000 записей на слот) делает это несущественным. Правильное
исправление при необходимости — дедлайны через loop.time(), НЕ
asyncio.sleep_until (такой функции нет в стандартной библиотеке — проверено).

# Kafka: KAFKA_CONTROLLER_QUORUM_VOTERS должен совпадать с адресацией

# INTERNAL-listener'а, а не с EXTERNAL

При введении раздельных INTERNAL/EXTERNAL listener'ов забыл
пересмотреть CONTROLLER_QUORUM_VOTERS. Он остался на localhost, а
INTERNAL-listener стал kafka:19092. Симптом — бесконечный цикл
"Discovered coordinator -> Marking the coordinator dead" у consumer group.
Правило на будущее: при добавлении EXTERNAL-listener'а все поля,
описывающие "внутреннюю" идентичность ноды (quorum voters,
inter-broker listener), должны использовать тот же адрес, что и
INTERNAL-listener, а не localhost.
