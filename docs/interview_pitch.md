## 2-минутный питч

Я построил event-driven платформу для биржевых данных: MOEX ISS API ->
Kafka -> PostgreSQL -> REST API. Два независимых продюсера пишут в один
топик по общему контракту: live читает реальные сделки через
недокументированный, но эмпирически подтверждённый параметр
`reversed=1` (обычная пагинация у этого эндпоинта MOEX не работает
вообще, пришлось разбираться самому). Replay проигрывает историю через
минутные свечи с синтетическим отрицательным `trade_id`, который
гарантированно не пересекается с реальными номерами сделок биржи.

Идемпотентность держится на PostgreSQL (составной PRIMARY KEY + ON
CONFLICT DO NOTHING), а не на логике продюсера - это превращает
at-least-once доставку Kafka в exactly-once на уровне итогового
состояния базы, без ручного управления офсетами.

ML - логистическая регрессия на lag-овых признаках, по модели на тикер, с
честной временной валидацией. Метрики скромные - я сознательно не выдаю
это за торговую стратегию, а прямо пишу в README, для каких тикеров
сигнал статистически различим, а для каких выборки пока не хватает.

## Типичные вопросы и ответы

| Вопрос                                                    | Ответ                                                                                                                                                                                                    |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Почему Kafka, а не прямая запись в БД?                    | Развязка по времени между продюсером и потребителем, единый источник для нескольких будущих потребителей, естественный буфер под всплеск нагрузки                                                        |
| Как получаете исторические данные для реплея?             | `candles.json` с явным `from`/`till` - `trades.json` не поддерживает произвольный диапазон дат в прошлом                                                                                                 |
| Как обеспечивается идемпотентность?                       | `PRIMARY KEY(trade_id, trade_time)` + `ON CONFLICT DO NOTHING` на уровне БД - не в коде продюсера/consumer'а                                                                                             |
| Почему модель такая простая?                              | Проект демонстрирует потоковую инфраструктуру, а не трейдинг-стратегию; честно заявляю это в README, а не маскирую метриками                                                                             |
| С какими реальными проблемами столкнулись при разработке? | Например: `KAFKA_CONTROLLER_QUORUM_VOTERS` был рассинхронизирован с адресом INTERNAL-listener'а - нашёл через анализ бесконечного цикла переподключения consumer-группы в логах, а не через документацию |
